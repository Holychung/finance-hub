# 數字的慣例

帳本裡每個數字代表什麼，以及為什麼有些數字故意不存在。這幾條決定了餘額、淨值和圖表怎麼
算，改動之前先讀。

## 金額一律用原幣，不折算

對帳單寫 58,420.15 USD，帳本就顯示 58,420.15 USD。總覽是**一個幣別一組數字**，沒有跨幣別
的單一總淨值——因為那個數字不存在。USD 和 TWD 沒有匯率就加不起來，硬湊一個出來只是把事實
變成估計值，而且那個估計值會在你編輯匯率時默默改變。

匯率還留著，但只剩一個用途：**判斷「台幣帳戶轉出」和「外幣帳戶轉入」是不是同一筆轉帳**。
那裡折算出來的數字不會進到任何餘額或總計。沒設匯率的話，跨幣別轉帳就認不出來，兩隻腳會各
自被算成一筆支出和一筆收入。只有單一幣別的話完全不用設。

匯率綁在自己的日期上：查某一天的匯率，拿到的是那天或那天以前最近的一筆。

## 信用卡和貸款的餘額是負數

餘額代表「這個帳戶對你值多少」，欠 1,234 就是 `-1,234`，所以淨值只要把全部餘額加起來就
好，不用去判斷帳戶類型。

代價是兩個地方要小心，而且錯了都不會有任何錯誤訊息：

- **期初餘額要填負的。** 對帳單上寫的是正數，照抄會讓淨值多算兩倍。新增帳戶時填了正數會
  當場提醒，之後總覽頁也會一直標著。但不會擋——真的溢繳的話那個正數是對的。
- **信用卡的網頁畫面和 CSV 檔，正負號是相反的——以檔案為準。** 網頁顯示的是「你欠多少」，
  所以消費是正的；CSV 已經是帳本的慣例，消費是負的，**不用勾「正負相反」**。（實際比對過
  同一筆交易：網頁上顯示正數，CSV 裡是負數。）別家發卡機構有可能是照網頁那種慣例匯出，而
  卡片檔沒有餘額欄可以逐行驗證，所以負債帳戶收到「流入筆數比流出多」的檔案時會跳提醒——
  那是唯一的保險，因為反過來的檔案每一行都合法。

## 持股和券商現金是分開的

買股票 = 券商帳戶現金流出（一筆交易）＋ 持股表股數增加。同一個幣別的淨值 = 該幣別所有帳戶
餘額 ＋ 該幣別所有持股市值，不會重複計算。市值永遠不會折進帳戶餘額裡。

**現價取「不晚於今天的最後一筆報價」**，跟匯率 `fx.on(d)` 綁在各自日期上是同一套；只有一個
刻意的差別——第一筆報價之前回 null、不把最早的往回拖，因為沒人報過價的那天就是沒有市值，
硬湊一個就是這本帳一直在避免的那種虛構。價格存在 `prices` 表（見下），一檔在多個券商共用
同一條序列。沒有任何報價時，退回 `holdings.last_price` 這個舊欄位。

**淨值走勢只畫帳戶淨額，不含持股。** 有了 `prices` 表，價格歷史已經有了；但誠實地把持股折進
走勢還需要「股數歷史」——每個月底那天到底持有幾股——那要等交易推導部位（lots）做完，現在
只存當前股數。缺一半就會畫出一條從來不存在的線，所以先維持只畫帳戶淨額。

**每個帳戶從自己的「期初日期」那個月才算進走勢。** 期初餘額是那一天的餘額，往前攤到圖表
開頭等於畫出一段你那時候根本沒有的錢。所以圖的起點是你最早那個帳戶開戶的月份，之後每多開
一個帳戶就多一階——那個階不是賺到的，是這本帳的涵蓋範圍變大了。要看哪幾個月真的有匯入
資料，看涵蓋度那頁。

## 幣是一種持股

錢包是一種帳戶類型（`wallet`），可以不屬於任何機構——自管的錢包本來就沒有。它通常沒有自己的
現金餘額，價值全在持股表裡；一個也放法幣的交易所帳戶比較像券商，歸哪一類由你決定。

幣本身是一筆 `market = 'CRYPTO'` 的持股，跟股票走同一套：一個幣別的淨值照樣是帳戶餘額加持股
市值，一枚用美元計價的 BTC 就落在美元那一欄，不需要新的機制。沒有報價來源——現價自己填，
`price_date` 說它有多舊。

新的只有三件事，而且錯了都不會有任何錯誤訊息：

- **數量的位數跟著持股走**（`holdings.decimals`，schema v8）。台股整股、美股四位、幣八位，
  這些是各市場的預設，每一筆都可以改。它只管顯示，存的數字不會被四捨五入。既有的持股升級後
  是四位，因為那本來就是它們顯示的位數。
- **市場一律大寫，清單以外的拒收。** 價格表一直都轉大寫，持股以前卻照收；存成 `crypto` 的持
  股會去找 `crypto` 底下的價格，而序列存在 `CRYPTO` 底下，於是永遠找不到，也永遠不會說。
- **幣別是市場給的預設，不是規則。** 以前是「美股就是美元，其他都是台幣」，第三個市場一律被
  當成台幣。台灣的交易所用台幣報價，所以表單讓你選。

單價至少顯示兩位，之後數字本身帶幾位就顯示幾位——一枚 0.1234 美元的幣以前會顯示成 0.12。

鎖倉或質押中的幣，把它所在的帳戶設成 `restricted`（見下面的 `accounts.access`）。

**錢包沒有對帳單可以匯**，所以它不在完整度那張表上（見下）。它的價值就是你手動填的數量和現
價，看最新的一筆就好。

## 餘額對帳是核心功能不是附屬

CSV 一定會漏（區間沒涵蓋、分頁沒撈完、格式怪的那幾行）。把網銀上的餘額記進來，系統就會指
出差多少。

## 帳本完整度：唯一會說「我不知道」的地方

上面每一個數字都是當帳本完整在算的。它不是 —— 一本 CSV 帳本只有某人記得去下載的那幾個
月，而**沒人下載的月份，跟什麼都沒發生的月份長得一模一樣**：一樣空、一樣沒有錯誤、餘額一
樣乾淨。餘額、淨值和走勢圖分不出這兩者，永遠也分不出來，因為差別不在資料裡。

`/coverage` 是唯一處理這件事的頁面：帳戶 × 月份，每格四種狀態。

| 狀態 | 意思 |
|---|---|
| 有資料 | 那個月有交易，格子裡是筆數 |
| 安靜（`–`） | 沒有交易，但有東西確認過它 —— 對帳紀錄，或一份涵蓋整個月的對帳單 |
| 只涵蓋一半（`◒`） | 有一份宣告過期間的對帳單伸進這個月，但沒有蓋完 |
| 缺口（`?`） | 沒有交易、沒有對帳、也沒有對帳單涵蓋到 —— 帳本對那個月一無所知 |
| 留白 | 帳戶當時還沒開，或已經停用 |

**沒有交易的月份不自動算缺口**，這是「安靜」自成一個狀態而不是比較淡的紅色的原因。帳戶本
來就可以整年不動，而那個月站著一筆對帳紀錄，代表銀行在那天跟帳本說法一致 —— 那比有一筆交
易還強，不是更弱。只有三樣都沒有的月份才算在你頭上。這條讓警告維持誠實：把安靜的月份確認
掉是使用者做得到的事，而不是一格他永遠清不掉、於是學會忽略的紅色。

**沒有對帳單可匯的帳戶不在這張表上**，也不算進任何一個數字，只在表的下面點名。這張表量的是
「對帳單有沒有匯進來」，而錢包根本沒有對帳單：它的價值是手動填的，只有最新的一筆有意義，留在
表上就是開戶以後每個月一格永遠補不了的缺口。哪些類型算這種，是 `shared/kinds.js` 裡每個類型
的 `statements` 旗標；目前只有錢包。

## 對帳單的涵蓋區間

`imports` 存著每次匯入的 `date_from` / `date_to`（schema v4）。一份對帳單橫跨了整個月、裡
面卻沒有那個月的交易，那是**銀行被問過而且說沒有交易** —— 跟有一筆交易是同一種答案。沒有
這個區間的話，那種月份跟「沒人下載」長得一模一樣，一個閒置的帳戶就會累積一排清不掉的紅格
子，除非使用者為每個安靜的月份手動記一筆對帳。格子的 `reason` 會說是哪一種確認：`check`
還是 `import`。對帳紀錄優先，因為銀行給了一個數字，那是比較強的說法。

**區間算的是檔案裡的每一行，不是匯進去的那幾行。** 重複的行照樣證明那份對帳單涵蓋到那個
日期，被拒收的位移行也是。只算匯進去的，區間會在每次期間重疊時縮水 —— 而重疊是常態。

## 宣告的期間 vs 推算的期間

`period_kind`（schema v5）記著這個區間是怎麼來的，而這決定它可以被相信到什麼程度。

**推算的（`derived`）只能整月整月地相信。** 一份從 12 號開始的對帳單，對那個月的前 11 天
什麼都沒說 —— 檔案裡那幾天沒有資料列，而「沒有資料列」正好也是沒消費的半個月的樣子。邊緣
是資料列碰巧落在哪裡的產物，不是事實。相鄰的區間會先合併再判斷，因為 6/30 結束和 7/1 開始
的兩份檔案合起來才涵蓋得到七月，單獨哪一份都不行。

**宣告的（`declared`）連邊緣都算數。** 銀行的下載頁本來就會讓你選「Statement of 2026-08」
「Year to date」或自訂區間 —— CSV 不會寫，但按下去的人知道。匯入畫面就直接問，所以
2/16–3/15 的一期帳單真的表示二月的後半有涵蓋、前半沒有。**「只涵蓋一半」這個狀態只有宣告
過的區間生得出來**，推算的永遠不會產生它。

兩個附帶的規矩：

- **有任何一行落在宣告的期間外，就整份擋下來。** 那不是警告，那是宣告錯了的證明 —— 要嘛期
  間選錯，要嘛這份檔案不是你以為的那一份。照樣匯進去等於寫下一個檔案自己反駁的涵蓋宣稱。
- **「只涵蓋一半」不算進缺口數。** 它自己有一個 `partials` 計數。折進缺口裡的話，宣告期間
  ——一個提供更多資訊的動作——反而會讓頭條數字變大。

v4 的 backfill 一律是 `derived`，而且只能從留下來的交易反推，所以它的區間是**匯進去的**範
圍，會少算。那是對的方向 —— 它只可能少清掉一個缺口，不可能無中生有宣稱涵蓋過。回復掉的匯
入沒有交易可以反推，區間就留 null。

頭條數字是 `trailing_gap` —— 最後一筆之後連續幾個月沒有資料。「三月之後就沒匯了」會讓人去
下載對帳單；一個攤在兩年裡的缺口總數不會。

## 資料表

| 表 | 用途 |
|---|---|
| `institutions` | 機構（玉山銀行、Firstrade…） |
| `accounts` | 帳戶，含幣別、類型、期初餘額、`access`（這筆錢能不能動），退休金另有 `tax_status` 與 `unvested` |
| `txns` | 交易，原幣、正流入負流出，帶 `source` 與 `external_id` |
| `holdings` | 持股，數量／均價、市場（台股、美股、幣），`decimals` 是數量顯示的位數（`last_price` 是最新報價的快取，退而求其次用） |
| `prices` | 每檔每日報價，保留歷史，依「證券」而非「部位」建鍵（比照 `fx_rates`） |
| `fx_rates` | 每日匯率，保留歷史 |
| `balance_checks` | 對帳用的實際餘額 |
| `imports` | 匯入批次，可整批回復 |
| `mappings` | 記住的 CSV 欄位對應 |

`txns` 的 `source`（`manual` / `csv` / `api`）和 `external_id` 現在就留著，第二階段接券商
API 時不用動結構。`holdings.price_date` 同理。

## 這筆錢能不能動：`accounts.access`

`liquid`（可動用）或 `restricted`（受限制），schema v7。**受限制是指你和這筆錢之間有一道規則**
—— 年齡、通知期、提早解約的罰則，例如退休帳戶或鎖倉的幣。不是「不好賣」：一間房子沒有人攔
著你賣，它仍然是 `liquid`。

它是帳戶的屬性而不是一種帳戶類型，因為從類型去猜會在最要緊的地方猜錯：自管的錢包跟活存一
樣能動，鎖倉的部位則不能，兩者卻可能是同一種類型。

**淨值依它拆成兩半。** 每個幣別除了原本的總額，另外有 `liquid`（可動用）和 `restricted`
（受限制）兩塊，形狀跟總額一模一樣：帳戶、持股、未歸屬、依類型的分布。兩半是同一套加法、
只是用比較少的列——持股跟著它所在的帳戶走，未歸屬跟著它的計畫走——所以加起來一定等於總額。
總額還在，因為它還是真的，只是把這週能花的錢跟有規則擋著的錢混在一起。**絕不**用猜的稅率去
折現受限制的那一半，也不預估、不年化——跟沒有跨幣別總額是同一個理由。

總覽預設看「可動用」，因為那是打開這頁的人想知道的：我現在能用多少。上面一組分段按鈕切換
「可動用／受限制／全部」，頭條數字、組成、走勢、依類型的分布和帳戶表都跟著切。沒顯示的那一半
一定會在頭條下面點名（「另有受限制 $X，不在這個數字裡」），不會悄悄消失；帳本裡沒有任何受限
制的帳戶時，三個選項是同一個數字，按鈕就不出現。

API 收到清單以外的值會**拒絕**，不會默默當成 `liquid`：那正是會把一筆退休金悄悄放回可動用數
字裡、而畫面上什麼都看不出來的那種錯。

新帳戶沒指定的話，起始值跟著類型走：退休金從「受限制」開始，其他類型從「可動用」開始。這只
是起點，之後看的是帳戶自己的值——鎖倉的錢包得自己改，因為類型分不出它跟一般錢包。

## 退休金：`tax_status` 和 `unvested`

退休金是一種帳戶類型（401(k)、IRA、勞退），schema v9 多了兩個只有它用得到的欄位：

- **`tax_status`** —— `pretax`（稅前）、`roth`、`aftertax`（稅後），或不註明。**只是標示，永遠不
  進任何計算。** 稅前的餘額領出來會少一截，但少多少取決於一個沒人知道的稅率、在一個沒人知道的
  日期；套一個進去，機構給的數字就變成一個每次重猜都會動的估計值——跟沒有跨幣別總額是同一個
  理由。所以餘額永遠是對帳單上的數字，這個欄位只說它是哪一種數字。同樣餘額的 Roth 和稅前帳戶，
  算出來一模一樣。
- **`unvested`** —— 雇主提撥裡還沒歸屬、雇主還能收回的部分，照計畫文件上的數字填。**淨值會扣
  掉它，餘額不會。** 餘額是對帳單上的總額，對帳單把未歸屬的部分算在裡面，對帳也是拿這個總額在
  比；從餘額扣掉的話，每一次對帳都會剛好差這個數。所以它跟持股市值一樣在淨值那一層處理：同一
  個幣別的淨值 = 帳戶餘額 ＋ 持股市值 － 未歸屬，依類型的分布裡它是單獨一列負的「未歸屬」。
  淨值走勢是帳戶淨額，不扣它。負數和讀不懂的值會被拒絕，不會默默變成 0。

**計畫網站下載得到交易紀錄的話，直接匯入**（Fidelity 的格式見
[formats.md](formats.md#️-fidelity-401k轉換和已實現損益不是進出)）：提撥記成收入、配息記成
股利，基金之間的轉換和已實現損益不匯入。這樣匯進來的餘額是**放進去的錢**，不含基金的漲跌，
帳戶頁的走勢線也是這個數字；跟對帳單上的市值差多少，記一筆對帳就看得到，差額就是漲跌。只拿
得到餘額的話（例如勞退專戶），提繳和收益各記一筆交易。

退休金還留在完整度的表上，所以沒有任何交易的退休帳戶，每個月都會是缺口；要讓它跟錢包一樣
離開那張表，把它的 `statements` 旗標改成 false 就好。

## 結構怎麼改

`server/migrations.js` 是一張有順序的清單，從第 1 版到今天，**它就是 schema 本身**——
`db.js` 自己不建任何表。全新的檔案是第 0 版，從頭重放一遍就長出來；已經在用的帳本從它
停在的那一版接著補。新建和升級走同一條路，所以兩者不可能長得不一樣。

改結構就是在清單尾巴加一筆，不改別的地方。開 app 時（`require('./db')`）自動套用，沒有
哪條路徑能繞過去。幾條規則，每一條都有測試盯著：

- **只能往後加，不能改舊的。** 已經套用過的步驟是歷史；改掉第 2 步等於改寫別人的帳本
  「被告知已經有了什麼」，而且不會有任何地方報錯。
- **一步不該搬動任何一筆資料。** runner 會在交易裡比對每張表前後的筆數，對不上就整步
  回滾。真的要搬（例如補資料）的步驟得自己寫 `verify()` 說明正確的結果長怎樣——沒有
  一個「跳過檢查」的開關。
- **版本號跟著那一步在同一個交易裡寫進去。** 所以中途被砍掉的話，帳本會停在最後一個
  完成的版本，失敗的那一步一點痕跡都沒有，下次開起來從那裡繼續。
- **升級前會先拍一份快照**放到 `backups/`（見 [`data.md`](data.md)）；全新的檔案不會拍，
  空資料庫沒什麼好備份的。
- **比程式新的帳本不會被硬開。** 用舊版開一本新版建立的帳，會直接印出說明並停住，不會
  把今天格式的資料寫進一個沒有那些欄位的檔案。
